## アーキテクチャ

- フロント: Electron + React + TypeScript(electron-vite)。表示に専念する。
- バックエンド: Python(FastAPI / uvicorn)。zip 読み出し・画像処理・OCR・LLM 呼び出しを担う。
- ローカル LLM: llama.cpp の `llama-server` を起動して OpenAI 互換 API で呼ぶ。
  Vision モデルは `--mmproj` 付きで起動する(既存の `llm_server.py` / `llm.py`)。
- 重い処理(OCR・要約・埋め込み)は解析キュー(`analysis_queue.py`)で直列に実行する。

## ライブラリの構成

管理ルート直下に本ごとのフォルダを作る。**本フォルダが正本、library.db は索引**。

```
<管理ルート>/
├─ .book-viewer/
│   ├─ library.db            索引・検索・読書位置・しおり・埋め込み(作り直せる部分が中心)
│   └─ thumbnails/           サムネイルキャッシュ
└─ <書名>/
    ├─ book.json             ID・書名・著者・書字方向・元ファイル名・取り込み状態・章構成
    ├─ source/
    │   └─ original.zip      元アーカイブ(変更しない)
    ├─ pages/                ページ単位の本文 0001.md …(本文の正本・手修正の対象)
    ├─ figures/              切り抜いた図 p0042-1.png …(ページ番号-連番)
    ├─ summaries/            [予定] 章ごと・本全体の要約
    └─ book.md               [予定] 全ページを結合した書き出し(生成物)
```

- 本の ID は取り込み時の内容フィンガープリント(`fingerprint.compute`)。`book.json` に保存し、
  フォルダ名を変えても同じ本として再リンクする。
- 本フォルダ名は書名から作る(Windows で使えない文字は `_`、同名は `書名 (2)`)。
- 元のページ画像は展開せず、zip から都度読む(容量を倍にしない)。
- 本文中の画像は本フォルダからの相対パスで参照し、フォルダを移動しても切れないようにする。
- 本フォルダ方式より前の作品(ルート配下の zip を直接登録したもの)は DB に残っていれば
  そのまま読めるが、スキャンでは新たに登録しない。

### book.json(schema 1)

```json
{
  "schema": 1,
  "id": "<内容フィンガープリント>",
  "title": "気象学入門",
  "author": "",
  "writing_mode": "horizontal",
  "source": "source/original.zip",
  "original_filename": "2026-09-20_1911_気象学入門.zip",
  "page_count": 180,
  "imported_at": "2026-09-21T08:56:42+00:00"
}
```

取り込み状態・章構成などは、該当機能を作るときに項目を足す(`schema` を上げる)。

## 取り込み

- 一覧上部の `＋`(複数選択)またはウィンドウへのドロップで取り込む。
- 取り込み前のダイアログで書名・著者・書字方向を確認する。書名の初期値はファイル名から作り、
  先頭の日時プレフィックス(例: `2026-09-20_1847_`)を取り除く。
- 元ファイルは「コピーして残す」(既定)か「移動する」を選ぶ。管理ルート内の未取り込み
  アーカイブを案内から取り込むときは「移動する」を初期値にする。
- 同じ内容の本が既にあれば重複として知らせ、初期状態で取り込み対象から外す。
- API: `POST /api/library/inspect`、`GET /api/library/loose`、`POST /api/library/import`。

## 本文データ

- **ページ単位の Markdown が本文の正本**。1 ページだけの再 OCR・手修正ができ、原本画像との
  対応(原本表示 / テキスト表示の切り替え、しおり位置)も崩れない。
- 見出し・コードブロック・表・数式(`$...$`)・画像参照は Markdown で書く。
- ルビは `<ruby>漢字<rt>かんじ</rt></ruby>` の HTML を Markdown に埋め込む。表示ではそのまま使い、
  LLM に渡すときは取り除く。
- 図は bbox(ページ上の範囲)も保存し、切り抜きをやり直せるようにする。
- DB 側には検索用に、本文を数百字ずつに分けた chunk と埋め込みベクトルを持つ(予定)。

### 文字起こし

- 1 枚のスクリーンショット(= アーカイブの 1 ページ)ごとに Markdown にする
  (`backend/app/transcribe.py`)。解析キューのジョブ種別 `transcribe` として直列に処理する。
- サンプルのスクリーンショットは Kindle の画面そのもので、1 枚に見開き 2 ページ(または 1 ページ)と、
  上部の書名バー・下部の「ページ○/○」が入っている。
- **既定のエンジンは YomiToku**(`backend/app/layout_ocr.py`)。M1 の比較
  ([scripts/ocr-compare/](../../scripts/ocr-compare/README.md))で、誤字・欠落とも最少、
  1 ページ 1 秒未満、LLM の読み込みも不要だった。Vision LLM は言い換え・脱落が出やすく 20 倍以上遅い。
  - ヘッダー/フッター(書名バー・ページ表示)は YomiToku の `ignore_meta` で除く。ルビは今は落とす。
  - YomiToku は隣り合う段落を 1 つにまとめることがあるので、行ごとの座標から字下げを見て
    段落を分け直す。字下げなしで始まり前の段落が文の途中で終わっていれば、つなぐ
    (見開きの境目・図をはさんだ続き)。
  - 図・表の領域は切り抜いて `figures/` に保存し、`![キャプション](../figures/p0151-1.png)` で参照する。
    図に接した図番号で始まる段落と、「。」で終わらない短い段落をキャプションとみなす。
  - 文字の入った横長の「図」は節見出しの飾り枠とみなして見出しにする(ページ上端のものは柱として捨てる)。
- Vision LLM(設定で切り替え)は、電子書籍の画面の書名・ページ表示を指示で除き、見開きは書字方向に
  応じた順で読ませる。画像は最大 1.5 倍に拡大して渡す。図は `[図: キャプション]` だけ残す。
- API: `GET /api/works/{id}/text`、`GET /api/works/{id}/text/{n}`、`POST /api/works/{id}/transcribe`
  (`engine`: `yomitoku` / `vlm`)、`GET /api/works/{id}/figures/{name}`。

## 取り込み後の処理パイプライン(予定)

1. レイアウト解析: 本文・見出し・図・表・ヘッダー / ページ番号の位置を検出する(済: YomiToku)。
2. 図の切り抜き: bbox で元画像から切り出して `figures/` に保存する(済)。
3. 文字起こし: 本文を Markdown にする(済: YomiToku)。
4. ページのつなぎ: ページをまたぐ段落をつなぐ(ページ内の見開きの境目は済。ページ間は未)。
5. 章の検出: 目次ページや見出しから推定し、手で直せる UI を用意する。
6. 要約: 数ページ → 節 → 章 → 本全体と段階的に積み上げる(コンテキスト長の制約のため)。
7. 埋め込み: chunk ごとに `llama-server --embedding` でベクトルを作る。

OCR / レイアウト検出のモデルは入れ替わりが早いので、特定のモデルに依存しない作りにし、
実際の本のサンプル(縦書きを含む)で比較して選ぶ。VRAM は 48GB あり、30B 級の Vision モデルを
量子化して載せられる。
