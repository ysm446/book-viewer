## アーキテクチャ

- フロント: Electron + React + TypeScript(electron-vite)。表示に専念する。
- バックエンド: Python(FastAPI / uvicorn)。zip 読み出し・画像処理・OCR・LLM 呼び出しを担う。
- ローカル LLM: llama.cpp の `llama-server` を起動して OpenAI 互換 API で呼ぶ。
  Vision モデルは `--mmproj` 付きで起動する(既存の `llm_server.py` / `llm.py`)。
- 重い処理(文字起こし・章立てと要約・本文検索の索引)はジョブキュー(`jobs.py`)で直列に実行する。
  API は `/api/queue`(状態)・`/api/queue/cancel`・`/api/queue/clear`。

## ライブラリの構成

管理ルート直下に本ごとのフォルダを作る。**本フォルダが正本、library.db は索引**。

```
<管理ルート>/
├─ .book-viewer/
│   ├─ library.db            索引・検索・読書位置・しおり・埋め込み(作り直せる部分が中心)
│   └─ thumbnails/           サムネイルキャッシュ
└─ <書名>/
    ├─ book.json             ID・書名・著者・書字方向・元ファイル名・取り込み状態・章構成
    ├─ source/
    │   └─ original.zip      元アーカイブ(変更しない)
    ├─ pages/                ページ単位の本文 0001.md …(本文の正本・手修正の対象)
    ├─ figures/              切り抜いた図 p0042-1.png …(ページ番号-連番)
    ├─ summaries/            章ごとの要約 ch-p0030.md …(章の開始ページ)・本全体の要約 book.md
    └─ book.md               [予定] 全ページを結合した書き出し(生成物)
```

- 本の ID は取り込み時の内容フィンガープリント(`fingerprint.compute`)。`book.json` に保存し、
  フォルダ名を変えても同じ本として再リンクする。
- 本フォルダ名は書名から作る(Windows で使えない文字は `_`、同名は `書名 (2)`)。
- 元のページ画像は展開せず、zip から都度読む(容量を倍にしない)。
- 本文中の画像は本フォルダからの相対パスで参照し、フォルダを移動しても切れないようにする。
- 本フォルダ方式より前の作品(ルート配下の zip を直接登録したもの)は DB に残っていれば
  そのまま読めるが、スキャンでは新たに登録しない。

### book.json(schema 1)

```json
{
  "schema": 1,
  "id": "<内容フィンガープリント>",
  "title": "気象学入門",
  "author": "",
  "writing_mode": "horizontal",
  "source": "source/original.zip",
  "original_filename": "2026-09-20_1911_気象学入門.zip",
  "page_count": 180,
  "imported_at": "2026-09-21T08:56:42+00:00"
}
```

章立ては `chapters`(`[{title, page, level}]`、page は 0 始まり、level 1 = 章 / 2 = 節)と
`chapters_updated_at` に入る(schema は 1 のまま。任意項目として追加)。

## 取り込み

- 一覧上部の `＋`(複数選択)またはウィンドウへのドロップで取り込む。
- 取り込み前のダイアログで書名・著者・書字方向を確認する。書名の初期値はファイル名から作り、
  先頭の日時プレフィックス(例: `2026-09-20_1847_`)を取り除く。
- 元ファイルは「コピーして残す」(既定)か「移動する」を選ぶ。管理ルート内の未取り込み
  アーカイブを案内から取り込むときは「移動する」を初期値にする。
- 同じ内容の本が既にあれば重複として知らせ、初期状態で取り込み対象から外す。
- API: `POST /api/library/inspect`、`GET /api/library/loose`、`POST /api/library/import`。

## 本文データ

- **ページ単位の Markdown が本文の正本**。1 ページだけの再 OCR・手修正ができ、原本画像との
  対応(原本表示 / テキスト表示の切り替え、しおり位置)も崩れない。
- 見出し・コードブロック・表・数式(`$...$`)・画像参照は Markdown で書く。
- ルビは `<ruby>漢字<rt>かんじ</rt></ruby>` の HTML を Markdown に埋め込む。表示ではそのまま使い、
  LLM に渡すときは取り除く。
- 図は bbox(ページ上の範囲)も保存し、切り抜きをやり直せるようにする。
- DB 側には検索用に、本文を数百字ずつに分けた chunk と埋め込みベクトルを持つ(予定)。

### 文字起こし

- 1 枚のスクリーンショット(= アーカイブの 1 ページ)ごとに Markdown にする
  (`backend/app/transcribe.py`)。ジョブ種別 `transcribe` として直列に処理する。
- サンプルのスクリーンショットは Kindle の画面そのもので、1 枚に見開き 2 ページ(または 1 ページ)と、
  上部の書名バー・下部の「ページ○/○」が入っている。
- **既定のエンジンは YomiToku**(`backend/app/layout_ocr.py`)。M1 の比較
  ([scripts/ocr-compare/](../../scripts/ocr-compare/README.md))で、誤字・欠落とも最少、
  1 ページ 1 秒未満、LLM の読み込みも不要だった。Vision LLM は言い換え・脱落が出やすく 20 倍以上遅い。
  - ヘッダー/フッター(書名バー・ページ表示)は YomiToku の `ignore_meta` で除く。ルビは今は落とす。
  - YomiToku は隣り合う段落を 1 つにまとめることがあるので、行ごとの座標から字下げを見て
    段落を分け直す。字下げなしで始まり前の段落が文の途中で終わっていれば、つなぐ
    (見開きの境目・図をはさんだ続き)。
  - 図・表の領域は切り抜いて `figures/` に保存し、`![キャプション](../figures/p0151-1.png)` で参照する。
    図に接した図番号で始まる段落と、「。」で終わらない短い段落をキャプションとみなす。
  - 文字の入った横長の「図」は節見出しの飾り枠とみなして見出しにする(ページ上端のものは柱として捨てる)。
- Vision LLM(設定で切り替え)は、電子書籍の画面の書名・ページ表示を指示で除き、見開きは書字方向に
  応じた順で読ませる。画像は最大 1.5 倍に拡大して渡す。図は `[図: キャプション]` だけ残す。
- 本文の手修正: テキスト表示のページごとの「編集」(左に原本、右に Markdown)。YomiToku の行ごとの
  確信度(`rec_score`)が 0.6 未満の本文の行を「要確認」として `pages/0001.json` の `low` に残す
  (サンプルでは誤読がこの範囲に集まっていた)。保存すると `edited: true` になり、直した行は `low` から外れる。
  全ページのやり直しは `edited` のページを飛ばす。
- ページ間のつなぎ: 本文の正本はページごとのまま、LLM・索引・検索に渡すときに `transcribe.join_pages` で
  つなぐ。前のページの最後の段落が文の途中(「。」や「」」などで終わらない)で、次のページが本文の段落で始まれば
  続きを前のページ側に寄せる。YomiToku はページ先頭の段落が字下げなしかを `pages/0001.json` の
  `head_continues` に残し、字下げありならつながない。「。」を含まない並びや、句読点の無い長い段落
  (奥付・目次・参考文献・表の文字)はつながない。チャットでは今のページまでの間だけでつなぐ。
- API: `GET /api/works/{id}/text`、`GET|PUT /api/works/{id}/text/{n}`、`POST /api/works/{id}/transcribe`
  (`engine`: `yomitoku` / `vlm`)、`GET /api/works/{id}/figures/{name}`。

## 取り込み後の処理パイプライン(予定)

1. レイアウト解析: 本文・見出し・図・表・ヘッダー / ページ番号の位置を検出する(済: YomiToku)。
2. 図の切り抜き: bbox で元画像から切り出して `figures/` に保存する(済)。
3. 文字起こし: 本文を Markdown にする(済: YomiToku)。
4. ページのつなぎ: ページをまたぐ段落をつなぐ(済。ページ内の見開きの境目は文字起こしで、ページ間は
   LLM・索引・検索に渡すときに `transcribe.join_pages` で。ページのファイルは分けたまま)。
5. 章の検出: 目次ページや見出しから推定する(済: LLM)。手で直す UI(済)。
6. 要約: 章ごと → 本全体(済。長い章は分けて要点を出してからまとめる)。
7. 埋め込み: chunk ごとに `llama-server --embedding` でベクトルを作る(済)。

OCR / レイアウト検出のモデルは入れ替わりが早いので、特定のモデルに依存しない作りにし、
実際の本のサンプル(縦書きを含む)で比較して選ぶ。VRAM は 48GB あり、30B 級の Vision モデルを
量子化して載せられる。

### 章立てと要約(M4 の最初の版)

- `backend/app/structure.py`。ジョブ種別 `structure`(LLM が必要)。
- 章立て: 目次ページ(前のほうで「目次」を含むページとその後 4 ページ)、各ページの見出し(`## `)、
  本文の少ないページの図の文字(章の扉)をページ番号付きで LLM に渡し、章(level 1)と節(level 2)の
  開始ページを JSON(json_schema)で返させる。範囲外・重複を除き、最初の章の前は「前付け」で補う。
  - 章の扉や目次は YomiToku では図として取られるので、文字起こしでキャプションの無い図には
    図の中の文字を代わりに入れる(`layout_ocr.py`)。
- 要約: 章ごとに本文を渡して「概要 2〜4 文・要点・キーワード」を作る。コンテキスト長の 6 割
  (4,000〜40,000 字)を超える章は、分けて要点を出してからまとめる。最後に章の要約から本全体の要約。
  `redo=False` なら既存の章の要約は作り直さない。
- 「三つの石で地球がわかる」(178 ページ)で、第1〜6章・終章・あとがきの開始ページが正しく取れた。
  「序章」は「はじめに」という名前になった(名前の誤りは手修正 UI で直せるようにしたい)。
  Qwen3.8-27B で章立て 66 秒、要約 137 秒。
- 章立ての手修正: 目次パネルの「編集」。`PUT /api/works/{id}/structure/chapters` で保存する。
  要約を作ったときの章の範囲を `summaries/index.json` に残し、範囲が変わった章の要約と本全体の要約は
  使わない(保存時に消す)。範囲が同じなら名前を変えても要約は残る。
- API: `GET /api/works/{id}/structure`、`POST /api/works/{id}/structure`(`redo`)、
  `PUT /api/works/{id}/structure/chapters`。
- 画面: リーダーの「目次」パネル(`TocPanel.tsx`)。

### 本のチャット(最初の版)

- `chat._build_chat_messages`(`backend/app/chat.py`): system に「本の情報」(書名・著者・ページ数・今のページ)と、
  文字起こし済みの本文のうち今のページまでを、近いページから `context_chars` 文字まで入れる。
  先のページは入れない。本文が無ければ、その旨を読者に伝えるよう指示する。
- `context_chars` はフロントがコンテキスト長の半分(2,000〜60,000 字)を渡す。
- 図は `[図: キャプション]`、ルビは落として渡す。
- 読み終えた章(今のページより前で終わる章)の要約を、予算の 1/3 まで前置きする。今読んでいる章の
  題名も渡す。先の章と本全体の要約は渡さない。
- 本文検索(`backend/app/embedding.py`): 本文(図は [図: …]、見出しは【…】)を段落単位で 500 字前後の
  まとまりに分け(ページはまたがない)、埋め込みベクトルを `chunks` に、本文の指紋を `chunk_index` に保存する。
  埋め込みモデルはモデル置き場の名前に embed を含む GGUF を自動で選び、会話用とは別の llama-server
  (`--embedding --pooling last`、ポート 8091)で必要なときだけ起動する(会話用のモデル一覧からは外す)。
  質問には Qwen3-Embedding の指示文を付けて埋め込み、今のページまでのまとまりから内積で上位を選ぶ。
  チャットでは予算の 1/4 までを「質問に関係しそうな本文」に使い、今のページ付近として渡すページは除く。
  「三つの石」(340 まとまり)で索引 17.5 秒、検索 0.05 秒前後。今のページから遠い内容
  (p.101 で p.35 の蛇紋岩の利用)を根拠のページ付きで答えられるようになった。
- ジョブ種別 `index`。API: `GET|POST /api/works/{id}/index`。本文を直したり文字起こしを
  進めたりすると `stale` になり、チャット欄で作り直しを促す。

### 全文検索

一覧の検索は `search.py`(FTS5 trigram)。書名・著者・本全体と章の要約・文字起こしした本文を 1 行に
まとめて索引にする。スキャン時と、文字起こし・章立てと要約のジョブが終わったときに作り直す。
