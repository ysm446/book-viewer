# plan — 実装方針と優先順位

作成日時: 2026-09-21 17:59
更新日時: 2026-11-17 10:39

目的と完成形は [goals.md](goals.md)、現在の進捗は [progress.md](progress.md)。

## アーキテクチャ

- フロント: Electron + React + TypeScript(electron-vite)。表示に専念する。
- バックエンド: Python(FastAPI / uvicorn)。zip 読み出し・画像処理・OCR・LLM 呼び出しを担う。
- ローカル LLM: llama.cpp の `llama-server` を起動して OpenAI 互換 API で呼ぶ。
  Vision モデルは `--mmproj` 付きで起動する(既存の `llm_server.py` / `llm.py`)。
- 重い処理(文字起こし・章立てと要約・本文検索の索引)はジョブキュー(`jobs.py`)で直列に実行する。
  API は `/api/queue`(状態)・`/api/queue/cancel`・`/api/queue/clear`。

## ライブラリの構成

管理ルート直下に本ごとのフォルダを作る。**本フォルダが正本、library.db は索引**。

```
<管理ルート>/
├─ .book-viewer/
│   ├─ library.db            索引・検索・読書位置・埋め込み(作り直せる部分が中心)
│   └─ thumbnails/           サムネイルキャッシュ
└─ <書名>/
    ├─ book.json             ID・書名・著者・書字方向・元ファイル名・取り込み状態・章構成
    ├─ bookmarks.json        しおり(人が付けたデータなので DB ではなくここが正本)
    ├─ highlights.json       ハイライトとメモ(同上。「ハイライト」の節)
    ├─ source/
    │   └─ original.zip      元アーカイブ(変更しない)
    ├─ pages/                ページ単位の本文 0001.md …(本文の正本・手修正の対象)
    ├─ content.json          アプリ用の本文(pages/ と章立てから作る生成物。表示・検索・LLM の材料)
    ├─ corrections.json      誤字の自動補正(ブロックごと。戻した補正も残すので消すと読み直しになる)
    ├─ figures/              切り抜いた図 p0042-1.png …(ページ番号-連番)
    ├─ summaries/            章ごとの要約 ch-p0030.md …(章の開始ページ)・本全体の要約 book.md
    └─ book.md               [予定] 全ページを結合した書き出し(生成物)
```

- 本の ID は取り込み時の内容フィンガープリント(`fingerprint.compute`)。`book.json` に保存し、
  フォルダ名を変えても同じ本として再リンクする。
- 本フォルダ名は書名から作る(Windows で使えない文字は `_`、同名は `書名 (2)`)。
- 元のページ画像は展開せず、zip から都度読む(容量を倍にしない)。
- 本文中の画像は本フォルダからの相対パスで参照し、フォルダを移動しても切れないようにする。
- 本フォルダ方式より前の作品(ルート配下の zip を直接登録したもの)は DB に残っていれば
  そのまま読めるが、スキャンでは新たに登録しない。
- 人が付けた作り直せないデータ(しおり、ハイライト・メモ)は本フォルダに置く。
  しおりは `bookmarks.json`(`{schema: 1, bookmarks: [{id, page, note, created_at}]}`、`backend/app/bookmarks.py`)。
  以前は DB の `bookmarks` テーブルにあり、本フォルダを初めて読むときにファイルへ移して DB の行は消す。
  本フォルダが無い旧方式の作品だけは DB のまま。

### book.json(schema 1)

```json
{
  "schema": 1,
  "id": "<内容フィンガープリント>",
  "title": "気象学入門",
  "author": "",
  "writing_mode": "horizontal",
  "source": "source/original.zip",
  "original_filename": "2026-09-20_1911_気象学入門.zip",
  "page_count": 180,
  "imported_at": "2026-09-21T08:56:42+00:00"
}
```

章立ては `chapters`(`[{title, page, level}]`、page は 0 始まり、level 1 = 章 / 2 = 節)と
`chapters_updated_at` に入る(schema は 1 のまま。任意項目として追加)。
本の言語は `language`(`"ja"` / `"en"`。無ければ日本語。schema は 1 のまま)。

## 取り込み

- 一覧上部の `＋`(複数選択)またはウィンドウへのドロップで取り込む。
- 取り込み前のダイアログで書名・著者・書字方向を確認する。書名の初期値はファイル名から作り、
  先頭の日時プレフィックス(例: `2026-09-20_1847_`)を取り除く。
- 元ファイルは「コピーして残す」(既定)か「移動する」を選ぶ。管理ルート内の未取り込み
  アーカイブを案内から取り込むときは「移動する」を初期値にする。
- 同じ内容の本が既にあれば重複として知らせ、初期状態で取り込み対象から外す。
- API: `POST /api/library/inspect`、`GET /api/library/loose`、`POST /api/library/import`。

## 本文データ

- **ページ単位の Markdown が本文の正本**。1 ページだけの再 OCR・手修正ができ、原本画像との
  対応(原本表示 / テキスト表示の切り替え、しおり位置)も崩れない。
- 見出し・コードブロック・表・数式(`$...$`)・画像参照は Markdown で書く。
- ルビは `<ruby>漢字<rt>かんじ</rt></ruby>` の HTML を Markdown に埋め込む。表示ではそのまま使い、
  LLM に渡すときは取り除く。
- 図は bbox(ページ上の範囲)も保存し、切り抜きをやり直せるようにする。
- DB 側には検索用に、本文を数百字ずつに分けた chunk と埋め込みベクトルを持つ(予定)。

### 文字起こし

- 1 枚のスクリーンショット(= アーカイブの 1 ページ)ごとに Markdown にする
  (`backend/app/transcribe.py`)。ジョブ種別 `transcribe` として直列に処理する。
- サンプルのスクリーンショットは Kindle の画面そのもので、1 枚に見開き 2 ページ(または 1 ページ)と、
  上部の書名バー・下部の「ページ○/○」が入っている。
- **既定のエンジンは YomiToku**(`backend/app/layout_ocr.py`)。M1 の比較
  ([scripts/ocr-compare/](../../scripts/ocr-compare/README.md))で、誤字・欠落とも最少、
  1 ページ 1 秒未満、LLM の読み込みも不要だった。Vision LLM は言い換え・脱落が出やすく 20 倍以上遅い。
  - ヘッダー/フッター(書名バー・ページ表示)は YomiToku の `ignore_meta` で除く。
  - ルビ: 段落の中身は `ignore_ruby` でルビを除いたものを使い、行(words)のうち本文の 0.7 倍より小さい
    かなだけの行をルビとして、親の行の右(縦書き)・上(横書き)にあるものを割り当てる。行の中の字の位置は
    均等割りで見積もり、ルビの範囲にかかる漢字の並びを親文字にする(読みが 1 字あたり 2 字を超えれば隣の
    漢字まで広げる)。読みが直後の本文と同じもの(送り仮名の読み違い)は捨てる。ルビの小書きの字
    (ゃゅょ)は大きい字で読まれることがある(ちゆうじよう)。
  - YomiToku は隣り合う段落を 1 つにまとめることがあるので、行ごとの座標から字下げを見て
    段落を分け直す。字下げなしで始まり前の段落が文の途中で終わっていれば、つなぐ
    (見開きの境目・図をはさんだ続き)。
  - 図・表の領域は切り抜いて `figures/` に保存し、`![キャプション](../figures/p0151-1.png)` で参照する。
    図に接した図番号で始まる段落と、「。」で終わらない短い段落をキャプションとみなす。
  - 文字の入った横長の「図」は節見出しの飾り枠とみなして見出しにする(ページ上端のものは柱として捨てる)。
- Vision LLM(設定で切り替え)は、電子書籍の画面の書名・ページ表示を指示で除き、見開きは書字方向に
  応じた順で読ませる。画像は最大 1.5 倍に拡大して渡す。図は `[図: キャプション]` だけ残す。
- 本文の手修正: テキスト表示のページごとの「編集」(左に原本、右に Markdown)。YomiToku の行ごとの
  確信度(`rec_score`)が 0.6 未満の本文の行を「要確認」として `pages/0001.json` の `low` に残す
  (サンプルでは誤読がこの範囲に集まっていた)。保存すると `edited: true` になり、直した行は `low` から外れる。
  全ページのやり直しは `edited` のページを飛ばす。
- ページ間のつなぎ: 本文の正本はページごとのまま、アプリ用の本文(下記)を作るときにつなぐ。
  前のページの最後の段落が文の途中(「。」や「」」などで終わらない)で、次のページが本文の段落で始まれば
  1 つの段落にする(判定は `transcribe.joins_previous`)。YomiToku はページ先頭の段落が字下げなしかを
  `pages/0001.json` の `head_continues` に残し、字下げありならつながない。「。」を含まない並びや、
  句読点の無い長い段落(奥付・目次・参考文献・表の文字)はつながない。
- API: `GET /api/works/{id}/text`、`GET|PUT /api/works/{id}/text/{n}`、`POST /api/works/{id}/transcribe`
  (`engine`: `yomitoku` / `vlm`)、`GET /api/works/{id}/figures/{name}`。

### 英語の本(`language: "en"`)

本ごとの言語で、文字起こしの後処理と Vision LLM の指示を切り替える。取り込みダイアログと「表示」で選ぶ
(`PUT /api/works/{id}/language`、`works.language` 列)。取り込み時の初期値は書名から推測する。英語の本は横書き。
エンジンの比較は [scripts/ocr-compare/](../../scripts/ocr-compare/README.md) の「洋書の結果」(The Giver の 4 ページで
YomiToku + 英語の後処理が WER 0.7%、1 ページ 1 秒前後。Vision LLM は 0.06% だが 15 倍遅く図を切り抜かない)。

- `layout_ocr.transcribe(raw, lang="en")`: 折り返しの行を空白でつなぐ(`_join`)。行末のハイフンで切れた語は、続きが
  小文字ならハイフンを外してつなぐ(本来のハイフン fat-bellied も外れるが、画像からは区別できない)。大文字で続けば残す
  (Pilot-in-Training)。ダッシュ(YomiToku は `―` で返す)は `—` にし、前後に空白を入れない。
- 文の終わりは `SENTENCE_END_EN`(`. ! ? " ” ’ )`)、キャプションは `Figure 1` / `Table 2` などで始まる段落。
- 飾り頭文字(本文の 1.8 倍より高い 1 字の段落)は右に続く段落の頭に付け直す。場面転換の飾り(`* * *`、`⁂`。YomiToku は
  「米」と読むことがある)は `***`(区切り線)にして前後をつながない。箇条書きの点(`·` `・` `•`)は `- ` のリストにする。
- YomiToku が見出しにしなかった章題(1 行で短く、本文より 1.2 倍以上大きい字)は見出しにし、文で終わる「見出し」は段落に戻す。
- ルビの処理はしない。画面の端の写り込みなど、英数字を含まない 2 字以下の段落は捨てる。
- ページをまたぐ段落のつなぎ(`transcribe.joins_previous(..., lang)`・`content.build_blocks(..., lang)`)も英語の
  文の終わりで判定し、ページ末のハイフン(grand- / father)をつなぐ。`content.json` の指紋に言語を含める。
- 残っている誤り: スモールキャピタル(`IMMEDIATELY`→`mmEDATELY`。確信度が低いので「要確認」に出る)、
  飾り頭文字の後の空白(`ITwas`)。確信度の低い行だけ Vision LLM で読み直す組み合わせは今後。
- 今後: 言語をまたぐ本文検索(日本語の質問で英語の本文を探す)、確信度の低い行の読み直し、単語帳。

### 辞書(英語の本)

`backend/app/dictionary.py`。英和辞書は EJDict-hand(CC0)。初めて引いたときに GitHub の `src/a.txt`〜`z.txt` を
`models/dictionaries/ejdict/` に取得し、メモリに読み込む(約 4.6 万語、初回の取得込みで数秒)。
API は `GET /api/dictionary?word=`(書かれた形と、語尾を外した元の形の項目を最大 2 つ。意味は 8 件まで)。
語尾は -s / -es / -ies / -ed / -ied / -ing / -er / -est / -ly と子音の重なり(stopped → stop)を外して試す。
不規則な活用は辞書の項目(ran → runの過去形)に頼る。画面は `TextView` が `caretRangeFromPoint` で
ポインタの下の単語(ハイフンで分ける)を取り、`450ms` 止まったら引く。結果は開いている間キャッシュする。

### 日本語訳と対訳(英語の本)

`backend/app/translate.py`。ジョブ種別 `translate`(LLM が必要)。API は `GET /api/works/{id}/translation`、
`POST /api/works/{id}/translate`(`redo`)。

- 材料はアプリ用の本文のブロック(p / heading / list / quote。図・表・コード・数式・場面転換は訳さない)。
  原文を文に分け(`split_sentences`。略語 Mr. と頭文字 J. では分けない。No. / p. は直後が数字のときだけ略語)、
  番号付きの文を LLM に渡して「from〜to 番の文 ↔ 訳文」の組を JSON(json_schema)で返させる。組は原則 1 文ずつ
  (段落全体を 1 組にしないよう指示する)。文を順に漏れなく覆っていない組は捨て、次の実行で訳し直す。
- 一度に約 2,500 字の続いたブロックを渡し、直前の 2 ブロックの原文と訳を文脈に添える。固有名詞・作中の用語は
  LLM に `terms` で返させて訳語表(`glossary`)に溜め、原文に出てくる語だけを次のまとまりに渡す。
- 訳の種類: 訳し方の指示(`instructions`)ごとに訳を分ける。組み込みは「自然な訳」(natural)と「直訳」(literal)で
  `translate.BUILTIN_STYLES` に持ち、自分で作った種類は管理ルートの `.book-viewer/translation_styles.json`
  (`{styles: [{id, name, instructions, updated_at}]}`。API は `GET|PUT /api/translation-styles`)に置く。
  種類が書けるのは訳し方だけで、文の組・漏れなく覆う・強調の記号・訳語表・見出しの決まりは `_prompt` が固定で
  加える(訳し方と食い違うときはこちらを優先と指示する)。ブロックごとに指示の指紋 `style_hash` を残し、指示を書き直した
  あとに古い指示で訳したブロックを数える(`stale`。「訳し直す」の「指示を書き直す前の段落を訳し直す」)。
  表示・翻訳する種類は本ごとに選ぶ(「訳・辞書」の「訳の種類」)。
- 保存は本フォルダの `translation/<種類の id>.json`(`{schema, blocks: {本文の指紋: {head, src, pairs, model, style_hash, at}}}`)と、
  種類をまたいで共有する訳語表 `translation/glossary.json`。種類ができる前の `translation/ja.json` は、読むときに
  `natural.json` と `glossary.json` へ移す。
  ブロックは md の SHA-1 で引くので、`content.json` を作り直しても本文が同じブロックの訳は残る(文字起こしの
  やり直し・手直しで本文が変わったブロックだけ未訳に戻る)。まとまりごとに保存するので、止めても続きから訳せる。
- ストリーミング: まとまりの訳は `llm.chat_stream`(json_schema 付き)で受け取り、0.4 秒ごとに書きかけの JSON から
  組(from / to / ja。ja は書きかけでもよい)を正規表現で取り出して、メモリの途中経過に置く(`get_live`、
  `GET /api/works/{id}/translation/live`)。まとまりを保存したら消す。json_schema のストリーミングを受け付けない
  サーバ(400)は、まとめて受け取る(途中経過は出ない)。画面は翻訳中に 1 秒ごとに途中経過を取り、保存済みの訳に
  重ねて表示する。進み具合(保存したまとまり)が変わったら訳全体を読み込み直す。
- `get_translation` はブロックの並びに合わせて `{head, model, pairs: [{en, ja}]}`(未訳・訳さないブロックは null)と、
  訳したモデルごとのブロック数 `models` を返す。
- 段落の単位: 段落の右クリックのメニューから、その段落・今の画面の段落だけを訳す(`blocks` を渡す。未訳でも訳してあっても)。
- 訳し直し: `redo`(全部)と `blocks`(content.json の添字。ツールバーの「この画面を訳す」・段落の右クリック)。どちらも訳語表は残し、
  新しい訳が取れなかったブロックは前の訳のままにする。訳したモデルの名前(llama-server に読み込んだ GGUF の名前)を
  ブロックごとに `model` として残す(モデルを変えて訳し直したときに見分けるため。記録の無い古い訳は空)。
- 表示(`TextView`): 「表示」の「日本語訳」(原文 / 訳文 / 対訳、本ごと)と「対訳の単位」(文 / 段落 / 節)。
  位置の基準のブロック(`data-b`)はそのままに中身を差し替えるので、切り替えても読んでいた場所に戻る。
  節は見出し・場面転換までの訳文を、原文の後にまとめて出す(区切りの無い章は章全体)。単位を変えても訳し直さない。
- 確認: The Giver の 4 画面(46 ブロック・154 文)を Qwen3.8-27B で 167 秒、組は 148。
  1 冊(約 1,700 ブロック)で 1 時間半前後の見込み。

### アプリ用の本文(`content.json`)

Kindle と同じ考え方で、**原本のページ単位の文字起こし(正本)** と **アプリが使う本文(派生データ)** を分ける。
`backend/app/content.py` が `pages/*.md` と章立てから、段落・見出し・図などのブロックの並びを作り、
本フォルダの `content.json` に保存する。テキスト表示・チャット・要約・本文検索の索引・一覧の全文検索は
ページのファイルではなくこちらを材料にする。

- ブロック: `{page, kind, md, cont?, break?}`。`page` は原本の何ページから始まるか(0 始まり)、
  `kind` は p / heading / figure / table / list / quote / code / math。
- ページをまたいで切れた段落は 1 つのブロックにつなぐ(3 ページ以上にまたがってもよい)。続きがどのページの
  分かは `cont`(`[ページ, md の中の開始位置]`)に残す。`content.page_texts(max_page=…)` は先のページから
  取り込んだ続きを落として返す(チャットのネタバレ防止)。本文検索の `chunks.page_end` もここから決める。
- 章(level 1)の開始ページ以降で最初に始まるブロックに `break` を付ける(表示で改ページする)。
- 生成物なのでいつでも作り直せる。材料(ページの本文・補助情報の更新時刻と大きさ、章立て)の指紋
  `signature` が変わっていれば、読むときに作り直す(1 冊 0.1 秒未満。ジョブにはしない)。
- 原本のページ番号が、読書位置・しおり・章立て・根拠のページ・手修正の共通の座標。アプリが組んだ
  画面の番号は保存しない(ウィンドウの大きさや文字サイズで変わるため)。
- 今後、アプリの判断による整形(柱・ノンブルの取りこぼしの除去、見出しの判定の見直しなど)はこの層に足す。
  正本のページは変えない。OCR の誤字の自動補正は下の「誤字の自動補正」。
- API: `GET /api/works/{id}/content` → `{signature, pages_done, blocks}`。

### 誤字の自動補正(日本語の本)

`backend/app/proofread.py`。ジョブ種別 `proofread`(LLM が必要)。YomiToku は見た目の似た字を取り違える
(ブ↔プ・パ↔バ・ッ↔ツ・ー↔一・カ↔力・エ↔工 など)。アプリ用の本文の段落(p / heading / list / quote)を約 3000 字ずつ
LLM に渡し、この種の取り違えだけを文脈から見つけさせて直す。

- **候補を人に確認させない**。その代わり、直せるのは「似た字の組」(`proofread._GROUPS`)の 2 字の、1 字ずつの
  入れ替えだけに限る。LLM の答え `{id, wrong, right}` のうち、組に無い入れ替え・字数の変わる書き換えは捨てるので、
  言い換え・現代表記への書き換え(米→メートル など)は入らない。組は実際の本で見つけた取り違えを見て足していく。
  組どうしはつなげない(ソ↔ン と ン↔シ があっても ソ↔シ は認めない)。
- 字数が変わらないので、`cont` のページの区切りの位置もずれない。
- 保存は本フォルダの `corrections.json`(`{schema, blocks: {補正前の md の SHA-1: {fixes: [{pos, from, to, off?}], model, at}}}`)。
  LLM が読んだブロックは補正が無くても記録する(読み直さない)。`content.load` がブロックを組んだあとに当て、
  補正したブロックには `fixes`(`[{pos, from, to}]`)と `pk`(補正前の指紋)を付ける。記録した位置の文字列が今の本文と
  合わない補正は当てない。補正のファイルは content.json の指紋に入れる(無い本は指紋を変えない)。
- 文字起こしのやり直し・手直しで本文が変わったブロックは記録から外れ、次の補正でそのブロックだけ読み直す。
- LLM を読み込んでいれば、日本語の本の文字起こしのジョブの後に自動で積む。テキスト表示のツールバーの「誤字を補正」でも積める
  (まだ読んでいない段落があるときだけ出す)。
- 表示: 補正した語に `::highlight(text-fix)` の細い下線。クリックで「元の字 → 直した字」と「元に戻す」のメニュー。
  戻した補正は `off: true` として残し、読み直しても当て直さない。
- 補正した本文がそのまま表示・チャット・要約・検索・読み上げの材料になる。補正の前に付けたハイライトは、補正で
  ブロックの指紋が変わるので、文字列での付け直しになる(補正した語を含む範囲は「位置ずれ」になりうる)。
- サンプル(Gemma 4 31B Q4_K_M、think なし)では THE NVIDIA WAY の 30 ページで 67 か所を直し、誤った補正は見当たらなかった。
  約 5 万字で 90 秒前後。
- API: `GET /api/works/{id}/proofread`(`{total, checked, fixes}`)、`POST /api/works/{id}/proofread`(`redo`)、
  `PUT /api/works/{id}/proofread/fix`(`{block, pos, off}`)。

### テキスト表示のページ組み(リフロー)

`src/renderer/src/TextView.tsx`。原本のページ割りにとらわれず、アプリがページを組む。スクロールはしない。

- 組版は CSS の段組み(multi-column)に任せる。高さを固定した段組みに本文を流し、あふれた段を
  1 画面として `transform` でずらして見せる。横書きは段が右へ並び(1 画面に 1〜2 段)、縦書き
  (`writing-mode: vertical-rl`)は段が下へ並ぶ(1 画面 1 段)。段落の途中での画面分けはブラウザが行う。
- アプリの判断: 章の始まりは改ページ、見出しの直後では分けない(`break-after: avoid`)、図・表は
  途中で分けない(`break-inside: avoid`)、図はキャプションごと 1 画面に収まる大きさにする。
- 一度に組むのは区画(章ごと。章立ての無い本や長い章は 3 万字を超えた先の見出しの前、または 6 万字で区切る)。
  本を丸ごと組むと、ウィンドウの大きさを変えるたびの組み直しが重いため。
- 位置: 組んだあと各ブロックが何画面目にあるかを測る。画面の先頭のブロックを覚えておき、ウィンドウの
  大きさ・文字サイズ・組み方・本文が変わって組み直したら、そのブロックのある画面へ戻る。
  覚え直すのはページ送り・移動のときだけで、組み直しでは覚え直さない(組み直すたびに「画面で最初に始まる
  ブロック」を覚え直すと、同じ画面に入った前のブロックへ寄っていき、ウィンドウの大きさを変える間に大きく戻る)。
  リーダーには「画面の本文が原本のどのページまで進んだか」を伝え、読書位置・しおり・目次・チャットは
  原本のページ番号のまま動く。目次・しおり・スクラバーでの移動は、そのページから始まる最初のブロックへ。
- 本文の組み方(原本どおり / 横書き / 縦書き)・文字サイズ(14 / 16 / 18 / 20px)・書体・文字の太さ(書体に
  用意された太さと呼び名。`textFonts.ts` の `weights`)は「表示」で選ぶ
  (localStorage。本をまたいで引き継ぐ)。原本の書字方向(`writing_mode`)は文字起こしの読み順と
  「原本どおり」に使う。
- 操作: `←` `→`(縦書きは左が次)、`↑` `↓`、ホイール、本文の左右の余白のクリック。
- 文字起こし・やり直し・本文の手修正は原本のページ単位のまま(ツールバーに今の原本ページを出す)。
- 制限: 縦書きは 1 画面 1 段(見開き 2 ページの形にはしない)。再開の位置は原本のページ単位
  (ブロック単位の読書位置の保存は今後)。

### ハイライト

テキスト表示で本文の範囲を選んで色(黄 / 緑 / 桃)を付け、メモを添えられる。人が付けた作り直せないデータなので、
しおりと同じく本フォルダに置く(`highlights.json`、`backend/app/highlights.py`)。

- 保存: `{schema: 1, highlights: [{id, color, note, text, created_at, updated_at, parts}]}`。`text` は選んだ文字列
  (一覧・書き出し用。複数の段落にまたがるときは改行でつなぐ)。`parts` は段落(アプリ用の本文のブロック)ごとの範囲
  `{key, block, page, start, end, text, prefix, suffix}`。バックエンドは中身を解釈せず、形だけ確かめて保存する。
- 位置の記録: `content.json` は作り直されてブロックの添字が変わり、画面の番号はウィンドウの大きさで変わるので、
  どちらにも頼らない。
  - `key`: ブロックの Markdown の指紋(レンダラーで計算する 53 bit のハッシュ)。本文が同じブロックを探す。
  - `start` / `end`: ブロックの中の文字の位置。描画した本文の文字(ルビの読み `rt` と訳文 `.rf-ja` を除く)で数える。
  - `text` / `prefix` / `suffix`: 選んだ文字列と前後 32 字。本文が少し変わっても、ブロックの中から探し直せる。
  - `block` / `page`: 作ったときの添字と原本のページ。指紋が同じブロックが複数あるときに近いものを選び、
    指紋で見つからないとき(文字起こしのやり直し・手直し)は近くのページ(±3)で `text` を含むブロックを探す。
- 付け直し: ブロックは上の順で決め、画面では `start` / `end` の文字列が `text` と同じならそのまま、違えばブロックの中の
  `text` の出現から前後の文字列が最も合うものを選ぶ。見つからない範囲は描かず、一覧に「位置ずれ」と出す
  (付け直した位置は保存し直さない)。
- 描画: CSS Custom Highlight API(`::highlight(hl-yellow)` など。辞書・検索・読み上げと同じく DOM を変えないので
  組みは変わらない)。メモのあるハイライトは点線の下線を足す。描くのは今の区画だけ。
- 操作: 本文を選ぶと選択の終わりの近くに小さなメニュー(色 3 つ・メモ)。ハイライトをクリックすると同じメニューで
  色の変更・メモの編集・削除。メモがあるハイライトの削除は確かめる。英語の本で訳文だけを出している段落と訳文
  (`.rf-ja`)には付けない(原文に付ける)。
- 一覧: リーダー上部の「ハイライト(N)」でパネルを開く(目次と同じ `.reader-info`)。本の中の順に並べ、色・抜粋・メモ・
  原本のページ。クリックでその場所へ(画像表示ならそのページへ)。テキスト表示で付け直した結果(今のページ・位置ずれ)を
  リーダーへ伝えて一覧に出す。
- API: `GET /api/works/{id}/highlights`、`POST`(作る)、`PATCH /{hid}`(色・メモ)、`DELETE /{hid}`。
- 今後: チャットの文脈に入れる(「ハイライトした所だけで要点をまとめて」)、Markdown への書き出し、画像表示での印。

## 取り込み後の処理パイプライン(予定)

1. レイアウト解析: 本文・見出し・図・表・ヘッダー / ページ番号の位置を検出する(済: YomiToku)。
2. 図の切り抜き: bbox で元画像から切り出して `figures/` に保存する(済)。
3. 文字起こし: 本文を Markdown にする(済: YomiToku)。
4. ページのつなぎ: ページをまたぐ段落をつなぐ(済。ページ内の見開きの境目は文字起こしで、ページ間は
   アプリ用の本文 `content.json` を作るときに。ページのファイルは分けたまま)。
5. 章の検出: 目次ページや見出しから推定する(済: LLM)。手で直す UI(済)。
6. 要約: 章ごと → 本全体(済。長い章は分けて要点を出してからまとめる)。
7. 埋め込み: chunk ごとに `llama-server --embedding` でベクトルを作る(済)。

OCR / レイアウト検出のモデルは入れ替わりが早いので、特定のモデルに依存しない作りにし、
実際の本のサンプル(縦書きを含む)で比較して選ぶ。VRAM は 48GB あり、30B 級の Vision モデルを
量子化して載せられる。

### 章立てと要約(M4 の最初の版)

- `backend/app/structure.py`。ジョブ種別 `structure`(LLM が必要)。
- 章立て: 目次ページ(前のほうで「目次」を含むページとその後 4 ページ)、各ページの見出し(`## `)、
  本文の少ないページの図の文字(章の扉)をページ番号付きで LLM に渡し、章(level 1)と節(level 2)の
  開始ページを JSON(json_schema)で返させる。範囲外・重複を除き、最初の章の前は「前付け」で補う。
  - 章の扉や目次は YomiToku では図として取られるので、文字起こしでキャプションの無い図には
    図の中の文字を代わりに入れる(`layout_ocr.py`)。
- 要約: 章ごとに本文を渡して「概要 2〜4 文・要点・キーワード」を作る。コンテキスト長の 6 割
  (4,000〜40,000 字)を超える章は、分けて要点を出してからまとめる。最後に章の要約から本全体の要約。
  `redo=False` なら既存の章の要約は作り直さない。
- 「三つの石で地球がわかる」(178 ページ)で、第1〜6章・終章・あとがきの開始ページが正しく取れた。
  「序章」は「はじめに」という名前になった(名前の誤りは手修正 UI で直せるようにしたい)。
  Qwen3.8-27B で章立て 66 秒、要約 137 秒。
- 章立ての手修正: 目次パネルの「編集」。`PUT /api/works/{id}/structure/chapters` で保存する。
  要約を作ったときの章の範囲を `summaries/index.json` に残し、範囲が変わった章の要約と本全体の要約は
  使わない(保存時に消す)。範囲が同じなら名前を変えても要約は残る。
- API: `GET /api/works/{id}/structure`、`POST /api/works/{id}/structure`(`redo`)、
  `PUT /api/works/{id}/structure/chapters`。
- 画面: リーダーの「目次」パネル(`TocPanel.tsx`)。

### 本のチャット(最初の版)

- `chat._build_chat_messages`(`backend/app/chat.py`): system に「本の情報」(書名・著者・ページ数・今のページ)と、
  文字起こし済みの本文のうち今のページまでを、近いページから `context_chars` 文字まで入れる。
  先のページは入れない。本文が無ければ、その旨を読者に伝えるよう指示する。
- `context_chars` はフロントがコンテキスト長の半分(2,000〜60,000 字)を渡す。
- 図は `[図: キャプション]`、ルビは落として渡す。
- 読み終えた章(今のページより前で終わる章)の要約を、予算の 1/3 まで前置きする。今読んでいる章の
  題名も渡す。先の章と本全体の要約は渡さない。
- 本文検索(`backend/app/embedding.py`): アプリ用の本文(図は [図: …]、見出しは【…】)を段落単位で 500 字前後の
  まとまりに分け(始まりのページが同じブロックの中で)、埋め込みベクトルを `chunks` に、本文の指紋を `chunk_index` に保存する。
  次のページの書き出しをつないだまとまりは `chunks.page_end` に次のページを持ち、「今のページまで」の絞り込みで外す。
  埋め込みは日本語向けの Ruri v3(`cl-nagoya/ruri-v3-310m`、768 次元)を sentence-transformers で
  バックエンドの中で動かす(2026-10-21 に Qwen3-Embedding の GGUF + 埋め込み用 llama-server から切り替え)。
  モデルは `models/embeddings/` に Hugging Face のキャッシュ形式で置く。本文には「検索文書: 」、質問には
  「検索クエリ: 」を付けて埋め込み、今のページまでのまとまりから内積で上位を選ぶ。`chunk_index.model` が
  今のモデルと違う索引は検索に使わず、作り直しを促す。
  チャットでは予算の 1/4 までを「質問に関係しそうな本文」に使い、今のページ付近として渡すページは除く。
  「三つの石」(340 まとまり)で索引 17.5 秒、検索 0.05 秒前後。今のページから遠い内容
  (p.101 で p.35 の蛇紋岩の利用)を根拠のページ付きで答えられるようになった。
- ジョブ種別 `index`。API: `GET|POST /api/works/{id}/index`。本文を直したり文字起こしを
  進めたりすると `stale` になり、チャット欄で作り直しを促す。

### 全文検索

一覧の検索は `search.py`(FTS5 trigram)。書名・著者・本全体と章の要約・文字起こしした本文を 1 行に
まとめて索引にする。スキャン時と、文字起こし・章立てと要約のジョブが終わったときに作り直す。
スキャン時は `search_meta` に残した指紋(書名・著者・`pages/` `summaries/` のファイル数と更新時刻)が
同じ本は読み直さない(起動のたびに全冊の本文を読まないため)。索引の作り方を変えたら `search._INDEX_VERSION` を
上げる(指紋に入っているので、次のスキャンで全冊を作り直す)。

本文の検索結果の画面(`SearchResults.tsx`)は、同じ時に作るもう 1 つの索引 `passage_index`(FTS5 trigram。
アプリ用の本文のブロック 1 つが 1 行で、ブロックの添字と原本のページを持つ)を使う。`search_passages` は空白区切りの
語をすべて含む段落を探し(3 文字以上は MATCH、短い語は LIKE)、語の出てくる回数と段落の長さで並べ、本ごとにまとめる。
抜粋と一致の位置はバックエンドで作る(位置はコードポイント)。結果を開くとリーダーへ `{page, block, terms, seq}` を渡し、
テキスト表示はそのブロックへ移る(本文を直して添字がずれたら、同じページで語を含むブロックを探す)。
英語の本は訳文も `passage_ja`(訳の組の訳文をつないだ text と、組 [原文, 訳文] の JSON)に索引し、同じ語で探す
(原文と訳文の両方で一致した段落は原文の一致として 1 件に数える)。原文で一致した箇所には語を含む最初の文の訳の組
(短ければ次の組も。最大 200 字)を `ja` に、訳文で一致した箇所には一致した位置の組の原文を `snippet` に入れ、訳文の抜粋を
`ja` / `ja_marks` にする。訳の種類は読む画面の選択(localStorage)を知らないので、自然な訳 → 新しく書いた種類の順で使う。
翻訳のジョブの後と、`translation/` が変わった本のスキャン時に作り直す。

意味の近さ: 段落(アプリ用の本文のブロック。段落・見出し・箇条・引用・図のキャプションで 8 字以上)ごとに Ruri v3 の
埋め込みを `passage_vec` に持つ(チャットの `chunks` とは別。検索結果からその段落へ飛ぶため)。英語の本も原文のまま
埋め込む(日本語の質問でも上位に来ることを確かめた)。索引はキューのジョブ `vectors` で、文字起こしのジョブの後と、
スキャン後に古い本(`passage_vec_meta.signature` が content.json の指紋と違う・モデルが違う)を自動で積む。本文の指紋
(`hash`)が同じ段落は前のベクトルを使い回す。検索は質問をベクトルにしてルートの全段落の行列(メモリに持つ)と内積を取り、
上位 30 件(1 冊なら 50 件)を、いちばん近い段落から 0.05 以内で足切りする。語の一致の順位と RRF(1 / (60 + 順位) の和)で
混ぜ、語の一致しない段落は `match: "meaning"` として出す。埋め込みモデルを読めないときは語の一致だけで返し、理由を添える。

### 音声読み上げ

Irodori-TTS(日本語専用)を公式の OpenAI 互換サーバー Irodori-TTS-Server で動かし、`tts.py` が子プロセスとして
起動・停止する(`vendor/irodori-tts-server/`。アプリの `.venv` とは別の uv の環境。モデルは `D:\ai-models\tts\hf-cache`)。
テキスト表示がアプリ用の本文のブロックごとに `POST /api/tts/speak` で音声(opus)を取り、順に再生しながら画面を送る。
詳細は [../design/tts.md](../design/tts.md)。

### API の保護

Electron main が起動ごとに合言葉を作り、環境変数 `BOOK_VIEWER_TOKEN` でバックエンドへ渡す。
バックエンドは `/api/health` 以外で `X-Book-Viewer-Token` ヘッダかクエリ `token` を検査する
(`main.py` のミドルウェア)。レンダラは `api.ts` の URL 生成で常にクエリに付ける(`<img src>` でも使える)。
ブラウザで開いた無関係なページから localhost の API を叩かれるのを防ぐためのもの。
単体起動(環境変数なし)では検査しない。

## 読書ノート

### 読書ノート(人物・相関図・年表・用語)

LLM で本文から「いつ・誰が・何を」を抜き出し、本フォルダに Markdown でまとめる。出来事がいつのことか、
この人物は誰だったかを、読みながら確かめられるようにする。2026-11-17 に、根拠付きの人物一覧 →
人物間の関係 → 読書位置に応じた相関図の順で進める方針を確認。同日に人物一覧・関係抽出・相関図の最初の版を実装。
年表・用語・チャット連携などは引き続き拡張案。

**現在の実装**

- `backend/app/notes.py`、`routers/notes.py`、ジョブ種別 `notes`、`ReadingNotes.tsx`。
  `GET|POST|PATCH /api/works/{id}/notes` で取得・作成・設定と訂正の保存を行う。
- 正本は `notes/people.json`（schema 1）。解析区間ごとの根拠付き情報、モデル・生成日時、別管理の手修正、
  手動統合、読書ノート用の本ごとの `spoiler_guard` を持つ。チャットのネタバレ設定とは独立。
- 本文ブロックを最大 3,000 字の区間に分け、公開ページが同じ区間だけを最大約 5,000 字までまとめて抽出する。
  後のページの内容を同時に渡して前の人物説明へ混ぜさせない。根拠は区間単位で持ち、
  現在の章立てで表示を絞る。名前と引用の実在を確かめ、明記・推測・手修正を区別する。
  区間の指紋に本文と位置を含め、保存済み区間は再解析しない。停止は区間の処理境界で行う。
- 本文を変更した場合は指紋の一致する情報だけを表示し、更新時に未解析の区間を抽出する。
  旧情報と手修正はファイルに残すが、新しい根拠へ自動転用しない。破損した保存ファイルは上書きせずエラーにする。
- 表示範囲は「本全体 / この章 / この章まで」。ネタバレ防止 ON ならさらに現在の読書位置までに制限する。
  判明位置は原本ページ単位で、ページをまたぐ区間は末尾ページを基準に保守的に判定する。
  未読の別名による統合と章題も隠す。図は累積した関係の描写を併記し、作中時系列の状態を推定して上書きしない。
- 表記の違う同一人物は表示を組むときに自動でまとめる(保存データは変えず、再解析も不要)。
  区切り(`·` / `・` / 空白)の違い、4 文字以上の名前の小書き・濁点の揺れ(ファン / フアン、ブリエム / プリエム)、
  推測の別名のうち 1 文字違いのもの、名前の一部だけの表記(ジェンスン → ジェンスン·フアン)が対象。
  一部だけの表記は、初出時点で既出の氏名のうち該当が一人に決まるときだけまとめ(既出が無ければ最初に出た氏名)、
  複数いれば別人のまま残す。判定には公開済みの情報だけを使う。代表名は氏名(部品の多い表記)を優先する。
  同一人物同士になった関係は相関図から外す。
- 人物は情報の多い順に返す。その範囲に情報 3 件以上の人物がいれば、2 件以下の人物に `minor` を付け、
  画面は一覧・相関図とも初期表示で畳む(人物の絞り込みには常に出す)。情報の多い人物は先頭 5 件だけ表示する。
- 抽出の後に名前を整理する(`notes.tidy_names`)。本全体の人物(代表名・別表記・短い説明)の一覧を LLM に渡し、
  50 件ずつ「人物かどうか」と「一覧の中の同じ人物の別表記」を判定させ、`people.json` の `names`
  (代表名 → `person` / `same`)に保存する。判定済みの名前は問い合わせ直さない。
  同一人物の判定は、英字と日本語の組か、名前の部品を共有する・1 文字違いの組だけ採用する
  (正体の判明のような統合を LLM の知識で持ち込ませない)。両方の表記が公開済みになってからまとめる。
  人物でない項目は `thing` を付けて返し、画面は登場の少ない人物と一緒に畳む。
  API は未整理の名前の数 `untidy` を返す。
- 自動の整理の手修正: `names` の各名前に `person`(人物 / 人物以外)と `apart`(自動の統合から外す)を持つ。
  `apart` の表記は、表記の揺れ・別名・LLM の判定・名前の一部の規則のどれでもまとめず、手動統合だけが効く。
  利用者が直した名前は LLM の整理で上書きしない。
- 人物の紹介文: `POST /api/works/{id}/notes/summary`。表示中の範囲(読書位置・章の絞り込み後)の情報だけを
  LLM に渡して 2〜3 文にまとめ、`people.json` の `summaries`(人物 ID → 情報の指紋 `key` と `text`)に保存する。
  表示時は指紋が一致するときだけ返すので、先の位置で作った文が前の位置で出ることはない。
  情報が増える・訂正されると指紋が変わり、作り直しになる。人物ごとに保持するのは最新の 1 件。
- 手修正は説明の訂正、情報の除外・復帰、判明ページを指定した人物統合・手動統合の解除。
  一覧と相関図の根拠から本文へ移動でき、ノートを閉じた際は本文の組版と位置を保つ。

**作るもの**

- 年表: 出来事、本文での書かれ方(「その三年後」など)、正規化した年月日、根拠のページ。
  小説は語られる順と起きた順が違うので、起きた順に並べ替えられるようにする。ノンフィクションは実年代で並べる。
  相対的な表現から決めた日付は「推定」と分かるようにする。
- 人物: 名前、別名・呼び名、どういう人か、初出のページ。
- 関係: 誰と誰がどういう関係か、根拠の引用と本文位置。相関図の線から根拠の本文へ戻れるようにする。
- 用語: 作中や分野の言葉と、その説明。

**作り方**

- 解析対象は本全体(文字起こし済みの本文)とし、読書位置で解析を止めない。人物・関係は本ごとの永続データとして
  保存し、画面を開くたびに生成し直さない。解析済みの範囲を記録し、追加・変更された本文を更新対象にする。
- アプリ用の本文を短い区間に分けて LLM に渡し、json_schema で項目を返させる。
  区間ごとに保存して、止めても続きから作れるようにする。章別表示は保存した根拠の位置から組み立てる。
- 本文から取った項目は、根拠の引用も返させ、その文字列が本文に無い項目は捨てる
  (誤字の自動補正で「似た字の組」だけを通すのと同じく、LLM の答えを機械で確かめる)。
  引用の実在だけでは解釈の正しさは保証できないため、本文に明記された内容と推測を区別する。
- 保存は本フォルダの `notes/`。項目単位の JSON を正本にし、Markdown(年表・人物・用語)への書き出しは今後。
  人が直した項目は `edited` として、作り直しで上書きしない(ページ本文の手修正と同じ扱い)。
  自由に書くメモは別の md にする。

**画面と操作**

- メニューの「登場人物」から本文の表示領域を人物一覧に切り替える。本文へ戻ると元の読書位置から再開する。
- 「登場人物をまとめる」で本全体のデータ作成を開始する。作成後は更新操作とし、読書位置の進行だけでは再解析しない。
  処理中は進捗と停止操作を表示する。将来は同じ画面に「一覧 / 相関図」の切り替えを追加する。
- ネタバレ防止は表示時のフィルターとして扱う。既定は読書位置まで、解除すると保存済みの全情報を表示する。

**気をつける点**

- 由来を分ける: 項目ごとに「本文から(ページ付き)」「LLM の一般知識(未確認)」「自分で書いた」を持ち、表示でも区別する。
  ローカル LLM は実在の人物の生没年などをよく間違えるので、本文由来と混ぜない。
- ネタバレ防止: 保存範囲と表示範囲を分ける。全項目に原本の本文位置を持たせ、防止が有効なときは
  読んだ位置より先で明らかになる情報を表示前に除外する。チャットへの提供にも同じ制限を適用する。
  人物の初出だけでなく、説明・別名の同一人物判定・関係の各情報に、明らかになった本文位置を持たせる。
  後半の正体や関係を過去の人物説明に混ぜず、その時点までの情報で一覧と相関図を組み立てる。
  全体を統合した説明文に単一の初出位置を付ける方式は避け、情報ごとに根拠を保持する。
  同一人物の統合結果や表示名からも、未読部分で判明する別名・正体が漏れないようにする。
  小説では外部情報の補足を既定でオフにする(有名な作品は LLM が結末を知っている)。
- 外部情報: 「すべてローカルで完結する」の方針があるので、まずは LLM の知識に「未確認」を付けて出すだけにする。
  Web 検索で補うのは、本ごとに明示的にオンにする別の機能として考える。

**再利用**

- チャットの文脈: 読んだ位置までの人物と年表を入れる(「この人は誰」「これはいつの話」)。
- 本文中のポップアップ: 人物名・用語をクリックすると説明を出す(辞書のポップアップの仕組みを使う)。
- 翻訳・誤字補正との共有: 人物名の表を訳語表(`translation/glossary.json`)や固有名詞の補正の手がかりにする。
- 読書ノートの書き出し: 要約・年表・人物・自分のハイライトとメモを 1 つの md にまとめる(Obsidian で開ける)。
- 久しぶりに開いたとき: 「ここまでのあらすじと登場人物」を出す。
- 本をまたぐ利用: 同じ時代を扱う本の年表を重ねる、人物を横断して探す(全文検索の索引に入れる)。

**進める順**

1. 根拠付きの人物一覧: 本文から名前・呼び名・説明・初出を抽出し、引用と本文位置を保存する。
   リーダーの一覧から根拠へ戻れ、人が訂正・同一人物の統合をできるようにする。
   本フォルダの JSON を正本とし、手修正を保護する。読書位置による情報の制限もこの段階から扱う。
2. 人物間の関係: 人物同士の関係を根拠付きで抽出し、明記と推測、関係の変化を扱う。
3. 読書位置に応じた相関図: その時点までに分かっている人物と関係を表示し、選んだ人物の周辺に絞れるようにする。
4. 以降の拡張案: 年表・用語、Markdown 書き出し、チャットへの組み込み、本文中のポップアップ。
   外部情報の補足(未確認の表示付き)と、本をまたぐ年表はさらに後で検討する。
